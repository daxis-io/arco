# Retention step 4: restore excludes receipts, restore projection and audit, checkpoint certificate — implementation plan

> **Execution contract:** implement package-by-package with TDD, one implementer per package, a two-stage (spec, then quality) review after each package, and no package starting before the previous one is approved. Design: `2026-09-26-state-store-retention-design.md` (accepted). Steps 1 (PR #439), 2 (PR #442) and 3 (PR #444) are on `main`.

**Goal:** A format-9 restore never restores idempotency receipts and leaves none behind, so a replay after a restore re-applies; the catalog projection materializes every restore (a snapshot at the restore sequence plus one audit row for the restore) instead of quarantining it; checkpoints carry the horizon certificate on every capture path.

**Survey findings this plan rests on (main at f4f827b7):**
- Restore plan version 7 already exists (step 1 pinned `committed_at_ms`). Changing rendered restore bytes requires a new plan version, or in-flight v7 plans fail with "cannot reproduce deterministic candidate bytes" instead of being superseded.
- The format-9 restore source is a checkpoint's materialized state (`restore_source_values`, `live_entries_bounded`); writes are computed by `restore_writes(source, current)` and every write lands at the restore sequence. Expiry hints are reproduced. No domain hook exists to exclude keys.
- Receipts today: a receipt in current but not in the source is deleted; one present in both with identical bytes and hint is kept and keeps answering replays (the design forbids this); one in the source but purged in current is resurrected. Empty-base trap: when the head pointer is absent, writes are diffed against an empty `current` but applied over `candidate_parent` (the source lineage), so source-lineage receipts would survive a scan-only filter.
- Pre-existing defect: the restore commit's single outbox record (`restore:{id}:{attempt}:{domain}`, payload `ControlMvpRestoreNotice`) is not a `ProjectionIntentV1`, so `CatalogProjectionMaterializer::process` quarantines it as `INVALID_PROJECTION_INTENT`; the quarantine is sticky-terminal, the record is never acknowledged or trimmed, and no snapshot is published at the restore sequence. Step 3 did not cause this.
- Checkpoints carry `retention_horizon` and `validate_source` requires it to equal the manifest's, except `prepare_bounded_checkpoint`, which hard-codes `None` (test-only mixed capture path; capture fails on a horizon HEAD).
- Every restore source is pinned (checkpoint retention or a retained root), so no restore can resurrect a key at an old generation.
- No production composition registers restore participants yet; restore is reached from tests, benches and the S3 qualification binary.

**Scope decision on semantic Parquet retry acceptance.** Step 3 deferred "accept an existing projection Parquet file whose decoded rows match" to no later than step 4 because restore-emitted audit records might be written without snapshot files. Package B writes the restore's snapshot files before its audit file, exactly like a mutation, so the audit comparison is never the first to fire and the step-4 trigger disappears. The library-upgrade hazard itself is pre-existing (snapshot files compare bytes too, and the legacy tier-1 compactor shares `put_state_if_absent`); it stays a separate follow-up.

**Tech stack:** Rust 1.88, Tokio, Arrow/Parquet; kernel tests in `crates/arco-catalog/tests/state_store_control_mvp.rs` and `control_mvp.rs` unit tests; catalog tests in `crates/arco-catalog/tests/catalog_authority_control_v1.rs`; workspace restore tests in `crates/arco-catalog/tests/workspace_snapshot_restore.rs`.

## As implemented

### Package A (commit d8e91db2 and the review-fix commits 78ef271c and d885407b)

- **Policy type.** `RestoreKeyPolicy` lives in `control_mvp/restore_key_policy.rs` and is re-exported at the crate root. `RestoreKeyPolicy::excluding(prefixes)` canonicalizes beyond the plan: prefixes are sorted, deduplicated, and any prefix covered by a shorter excluded prefix is dropped, so equal key sets build equal policies and digests. `MAX_EXCLUDED_PREFIXES = 16` bounds the canonical set (duplicates and covered prefixes do not count); an empty prefix is a `Validation` error. `none()` is the default. `excludes`, `excluded_prefixes`, `excludes_nothing` (renamed from `is_none` in review) and `sha256` are public; `excluding_key_tag` is crate-private.
- **Digest framing.** Tag `arco/control-v1/restore-key-policy` through a new unscoped framing, `Canonical::unscoped` (tag and framing version 1 only: a policy belongs to a participant, not to a root, so no implementation, format or scope is bound), then the prefix count and each canonical prefix. Each domain tag is used with exactly one framing. The empty-policy and receipt-policy digests are pinned in unit tests against an independently built preimage.
- **`RestoreSourceScan`.** `restore_source_values(source, policy, now)` returns the filtered rows together with the policy that filtered them, so a render can never mix two policies. `live_entries_bounded(policy, ..)` drops excluded rows before charging the 1,000,000-row and 64 MiB budget.
- **Writes and the empty base.** `restore_writes(scan, current, candidate_parent)` diffs non-excluded keys only, then deletes every excluded key live in `candidate_parent` in one block. The base invariant (the candidate parent is `current`, or `current` is empty and the candidate parent is the source lineage) is stated and debug-asserted, so the plan's "live in current or in the candidate parent" reduces to the candidate parent.
- **Plan 8 and version-range helpers.** `RESTORE_PLAN_VERSION = RESTORE_PLAN_VERSION_V8 = 8`. `restore_key_policy_sha256` is required, validated as a prefixed digest, and exposed as `ControlMvpRestorePlan::restore_key_policy_sha256()`. Version 7 joins the supersession-only arm and keeps its `committed_at_ms` requirement. Review added `stamped_restore_plan_version` (7 through current) and `key_policy_bound_restore_plan_version` (8 through current), so field presence follows ranges that end at the current version and the next bump supersedes v8 instead of failing to decode it. `RESTORE_PLAN_VERSION_V7` is documented as unrelated to the bounded `ControlMvpRestorePlanV7`.
- **Policy mismatch (decision).** Inspection compares the plan's digest with the participant's policy beside the version, pointer and manifest checks. A mismatch is `Superseded`, so the driver replans; it is never a byte-mismatch invariant violation and never writes.
- **Landed version-8 plans inspect `Visible` whatever the policy (decision).** For a version-8 plan the lineage check runs before the policy check: the policy governs rendering, not recognition of a committed restore. Plans 1 through 7 return `Superseded` before the lineage check. A landed v7 plan now inspects `Superseded`, as a landed v6 plan does.
- **Bounded guards (extra; advance added in review).** Bounded authority-8 planning and advance refuse a participant whose policy excludes anything with `UnsupportedOperation` ("bounded authority-8 restore cannot honour a restore key policy") before any read or write, instead of silently restoring the excluded keys. A policy-free bounded restore is unchanged.
- **Capacity message (extra, review).** A restore whose writes overflow its single L0 keeps `Validation` and names the restore and its counts (`RestoreWriteCounts::l0_capacity_error`): `Control MVP restore {restore_id} attempt {attempt} of domain {domain} does not fit one L0 segment (puts: N, deletes: N, excluded-key deletes: N, plus one restore notice): {segment detail}`. HEAD does not move.
- **Catalog constructor (deviation).** A free function, `catalog_restore_participant(store) -> Result<ControlMvpRestoreParticipant>`, rather than a `ControlCatalogAuthority` method, because participants are built over a `ControlMvpStateStore`. It refuses a store outside the `catalog` domain with `Validation`. `catalog_restore_key_policy()` excludes tag 3 only. The S3 qualification binary restores the catalog through it; its assertions do not depend on receipts.
- **Fixture.** `v7_last_before_restore_key_policy.json` was captured from the code before the change.
- **Tests.** Planned (a) to (f): `restore_key_policy_deletes_excluded_keys_and_never_restores_them`; `restore_key_policy_tombstones_excluded_keys_of_an_empty_base_source_lineage`; `live_entries_bounded_drops_excluded_rows_before_charging_the_row_and_byte_budget` (unit, on the counting function directly); `a_restore_plan_binds_its_key_policy_and_a_different_policy_supersedes_it`; `literal_v7_restore_plan_fixture_is_supersession_only_and_pins_the_key_policy_binding` and `a_v7_plan_over_a_matching_source_is_superseded_and_never_applied`; `restore_without_a_key_policy_keeps_the_plain_rules_for_every_key`. (g) is `restore_never_restores_receipts_and_a_replay_re_executes`; it pins the re-execution as the catalog name conflict (`AlreadyExists { entity: "catalog", name: "analytics" }`) with no receipt committed, and checks that a tag-4 row in the checkpoint is kept and a current-only one deleted. Added: `restore_writes_delete_excluded_keys_live_in_the_candidate_parent_for_both_bases`, `restore_plan_field_presence_follows_version_ranges_through_the_current_version`, `restore_l0_capacity_errors_name_the_restore_and_its_write_counts`, `capacity_design::excluded_key_deletes_alone_can_exceed_one_restore_l0_with_small_injected_limits`, `authority8_bounded_restore_refuses_a_restore_key_policy`, `plan7_bounded_advance_refuses_a_restore_key_policy_before_any_write`, `catalog_restore_key_policy_excludes_only_the_receipt_prefix`, and the policy module's canonical-form, bound and pinned-digest tests. Existing tests changed only because they encoded the v7 version or field set (listed in d8e91db2); none encoded receipt-restoring behaviour. The `segment_row_expiries` helper became `segment_rows`.
- **Sizing (review).** Before this change the source scan charged receipts. At about 564 B per row its 64 MiB budget held about 119k receipts, below the ~180k live at the pilot rate, so pilot-rate restores already failed at plan time. Receipts no longer charge it, but their deletes share the single restore L0, whose 512 KiB index limit binds at roughly 390k live receipts. Each restore turns live receipts into tombstones that the horizon purges only after it passes the restore sequence (at least 30 days), adding up to ~180k retained rows for that period.

### Package B (commit 77cdb4c0 and the review-fix commit 8dab4f71)

- **Recogniser (deviation in shape).** Instead of a pure decoder, `ControlMvpStateStore::resolve_restore_notice_source(record) -> Result<Option<ControlMvpResolvedRestoreNotice>>` decodes and authenticates in one call, and `ControlMvpRestoreNoticeView` is reachable only through it. `ControlMvpProjectionOutboxRecord::claims_restore_notice()` (id prefix `restore:`) decides whether a record claims to be a notice; catalog intent ids never take that prefix. Checks: (1) the payload decodes as `ControlMvpRestoreNotice` (unknown fields are now denied; encoding is unchanged) and is byte-for-byte its canonical encoding; (2) the id is `restore:{restore_id}:{attempt}:{domain}` of the payload and a valid `RestoreAttemptIdentity`; (3) the domain is the store's; (4) the record's origin sequence is the result sequence; (5) an authenticated ancestry walk from the root the record was read at finds the commit manifest at the result sequence, skipping maintenance and horizon rewrites published at that sequence since; (6) that commit is a restore: its manifest id and the id of its transaction at that sequence carry the restore prefixes for that sequence, and the transaction's request id is the record id. Only manifests and transaction metadata are read. The returned token reads the restored state at the restore's own manifest, so a later horizon at that sequence does not change the snapshot.
- **Recogniser error mapping.** Checks 1 to 4 fail `Validation`. A well-formed record the lineage refutes (no or a foreign observed root, a root older than the result, checks 5 and 6, a checksum failure) fails `InvariantViolation`. Unreadable lineage (a missing or failing manifest on the path, an exhausted walk budget) is `AmbiguousAuthorityOutcome`. Every refusal names the record id.
- **Retryable missing transaction (review).** A missing restore transaction object is mapped from `NotFound` to `AmbiguousAuthorityOutcome`, like a missing manifest, so it is retried rather than quarantined. Review also fixed the lookup to the `tx_ref` at the result sequence; the first cut took the manifest's last one.
- **`INVALID_RESTORE_NOTICE` vs `INCOMPATIBLE_PROJECTION_INTENT`.** `process` settles authentication and publication separately through one `settle_failure` helper with the existing retryable set (`Storage`, `CasFailed`, `MaintenanceBackpressure`, `AmbiguousAuthorityOutcome`). A retryable error records `CATALOG_PROJECTION_FAILED` and fails the drain. A non-retryable authentication error quarantines `INVALID_RESTORE_NOTICE`. A non-retryable publication error quarantines `INCOMPATIBLE_PROJECTION_INTENT`, as for intents. The quarantine warn log gains `failure_code`. A record that does not claim `restore:` and does not decode as an intent is still quarantined `INVALID_PROJECTION_INTENT`, without a log line.
- **Quarantine pre-check (decision, review).** Before authenticating, a `restore:` record whose origin sequence already carries a terminal disposition for the same record id is reported quarantined without authentication or publication, whatever the code. Two reasons. A notice quarantined `INVALID_PROJECTION_INTENT` before this change would otherwise be materialized or quarantined again under a new code, and a second disposition at its sequence fails `validate_matching_quarantine`, which would fail every later drain. And re-authenticating a notice whose lineage later became unreadable would turn a settled quarantine into a drain failure. The pre-check covers `restore:` records only; intents keep the pre-existing re-processing (follow-up 5).
- **Shared publication path.** `materialize` and `materialize_restore` share `publish_projection(source token future, audit row)`: encode the audit row first, resolve the token and read the catalog state, write the snapshot under `catalog-parquet/{sequence:020}-{manifest_id}/` of the token, then the audit file, then the snapshot manifest (`publish_snapshot_manifest`, extracted). Success records the result sequence as applied.
- **Audit row.** `restore_audit_row`: `record_version` 1; operation id = the record id; family `restore_domain`; request digest = SHA-256 hex of the payload; actor `restore`; `occurred_at_ms` = the result manifest's `committed_at_ms` (the stamp the plan pinned); logical sequence and authority manifest of the result; no logical commit id. No schema change.
- **Path-safe names (review).** `audit_artifact_path` replaces every `:` of the operation id with `-` in the file name, because Hadoop-style path readers reject `:`; the row keeps the exact id. Intent ids (`op-…`) contain no `:`, so their names are unchanged, and names stay unique per sequence because a restore commit carries no intent.
- **No post-commit drain.** A restore commits through the restore participant, not the catalog authority, so no `CatalogProjectionNotifier` fires. The notice is materialized by the next drain: the scheduled worker, or the drain the next mutation wakes.
