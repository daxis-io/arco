# Retention step 3: receipt expiry, audit-row removal, audit projection — implementation plan

> **Execution contract:** implement package-by-package with TDD, one implementer per package, a two-stage (spec, then quality) review after each package, and no package starting before the previous one is approved. Design: `2026-09-26-state-store-retention-design.md` (accepted). Steps 1 (PR #439) and 2 (PR #442) are on `main`.

**Goal:** The catalog adapter stops writing audit rows to the authoritative KV and writes idempotency receipts with a 24-hour expiry hint; the catalog projection materializer appends every audit record to a day-partitioned `system.catalog.audit` Parquet artifact before it acknowledges the intent; a retention sweep ages audit partitions (default 400 days). No restore-path changes (the restore-emitted audit record moves to step 4 because the restore code was rewritten on `main` after step 2).

**Architecture:** `stage_commit_records` (`crates/arco-catalog/src/catalog_authority.rs` ~:2922) keeps the receipt (key tag 3) and the projection intent whose payload is the audit record, and drops the audit row (key tag 4) and its `assert_absent`. The receipt is written with `ArcoStateTxn::put_with_expiry` at `occurred_at_ms + 24 h` (format 9; the test-only bounded format 8 refuses expiry, so its v2 path keeps a plain put). `CatalogProjectionMaterializer::materialize` (~:1040) decodes the intent payload and writes one immutable Parquet file per intent under `control/v1/projections/catalog-audit/dt=YYYY-MM-DD/` (day of `occurred_at_ms`, UTC) with a does-not-exist precondition and byte-identical retry acceptance, exactly as the snapshot manifest is written, so artifact-before-ack ordering holds and at-least-once redelivery is idempotent. A retention sweep on the materializer deletes partitions older than the retention; the control-store worker calls it in its GC phase. Nothing under `control/v1/projections/` is touched by the kernel GC (domain-scoped to `control/v1/domains/<domain>`) or the legacy GC (`snapshots/` only).

**Tech stack:** Rust 1.88, Arrow/Parquet (already used by `parquet_util`), Tokio; test harness in `crates/arco-catalog/tests/catalog_authority_control_v1.rs` (`scoped_storage()`, `scope()`, `RecordingProjectionNotifier`, `commit_burst_and_settle`) and the worker binary's tests.

### Package A (commit e3371549 and the review-fix commit after it)

- **Completion.** The Package A implementer was interrupted mid-package; the lead finished it (commit e3371549), and a review round followed with the fixes recorded below.
- **Retired tag kept for the fixture.** `AUDIT_KEY_TAG` and `audit_key` were not removed. They survive under `cfg(any(test, feature = "test-utils"))` because the authority-8 synthetic-genesis cost fixture (`bounded_capacity_v2_record_pair`) models the pre-step-3 row shape its recorded bounded cost measurements were taken with. The format-9 `capacity_fixture_record` models receipts only. Tag 4 is documented as reserved forever: format-9 roots written before step 3 may still hold tag-4 rows, and nothing expires or deletes them.
- **Receipt retention contract.** `CATALOG_RECEIPT_RETENTION_MS` is re-exported at the crate root. A keyed request stays replayable with its original response for at least 24 hours from when the adapter accepted it (the audit record's `occurredAtMs`); the horizon adds its one-hour skew margin, so a receipt is first purgeable strictly after `occurredAtMs + 25 h`. The hint is written on format 9 only; the test-only bounded format 8 writes plain receipts. Once a receipt is purged its key is free: a different same-family request under that key is no longer an idempotency conflict, and an identical one re-executes. Unkeyed mutations also write a receipt (keyed by their random operation id) with the same expiry, so the horizon purges those too.
- **Deterministic operation ids (decision).** Keyed operation ids stay deterministic per (operation family, idempotency key), as the accepted design's family-qualified operation id requires, and the projection intent id equals the operation id. Consequence: a keyed request replayed after its receipt was purged re-executes under the same id. While the earlier intent is still retained in the outbox, staging fails closed with `CatalogError::AlreadyExists { entity: "projection intent", .. }` before commit (no receipt, no mutation). Once the materializer drains and trims that intent, the retry commits and stages a fresh outbox incarnation of the same id at a higher origin sequence. The downstream audit identity is therefore `(operation_id, logical_sequence)`, not `operation_id` alone; Package B's artifact path (`{source_logical_sequence:020}-{intent_id}.parquet`) already encodes that pair.
- **Tests rewritten** because they encoded audit rows in the KV: the cross-family idempotency test (now `shared_idempotency_key_across_families_keeps_every_intent_and_no_audit_row`: zero tag-4 rows, three audit intents with the three families); the lost-response reconciliation test (zero tag-4 rows, the intent's family); `control_bounded_parity` (no tag-4 write, and its undeclared-writes check enforces that none is written; the intent payload is still compared to the expected audit record); the bounded unit tests (audit history read from the notified intents); the `capacity_design` smoke test and the `gate7_capacity` probe (one receipt per mutation).
- **Tests added.** `receipt_expiry_tests` (exact staged write shape on both formats; committed state holds the receipt and no audit row). `receipts_expire_after_the_retention_window_and_the_replay_reapplies` pins the catalog name conflict (`AlreadyExists { entity: "catalog", name: "analytics" }`): the command's name check runs before the commit records are staged, so it fires even though the first intent is still retained. `a_purged_receipt_lets_a_keyed_patch_reapply_once_its_intent_is_trimmed` walks the post-purge path above (two receipts purged, the replay fails closed on the intent id with no new receipt, then drain and trim, then the replay commits one receipt and one intent of the same id at origin sequence 4 against the original 2). `a_receipt_becomes_purge_eligible_strictly_after_twenty_five_hours` pins the horizon boundary (no eligible row at `occurredAtMs + 25 h`, eligible one millisecond later).

### Package B (commit fa1b3986 and the review-fix commits ee568f31 and 5d26668e)

- **V1-only decoder (decision).** The first cut decoded `CatalogAuditRecordV1` and fell back to `CatalogAuditRecordV2`. Review narrowed `decode_catalog_audit_row` to V1 only: bounded V2 records ride only `ProjectionIntentV2` envelopes on format-8 roots, which refuse V1 outbox staging and reads, so a V2 record inside a V1 envelope is malformed. The decoder also requires `version == 1`, operation id = intent id, logical sequence = the intent's source logical sequence, and authority manifest id = the intent's source authority manifest id. Every failure is `CatalogError::Validation`, which the materializer quarantines as `INCOMPATIBLE_PROJECTION_INTENT`. `CatalogAuditRow::logical_commit_id` and its nullable column stay in `catalog_audit_schema()`, reserved for a future materializer of format-8 intents and always null today. The artifact path is built from the decoded, checked row.
- **Decode before write.** `materialize` decodes the audit record, computes its path and encodes its Parquet bytes before it reads the source state or writes any snapshot file, so a malformed payload is quarantined without leaving snapshot files behind. Write order: the snapshot files, then the audit file (`publish_audit_artifact`), then the snapshot `manifest.json`. A published manifest therefore implies an audit file, and every acknowledged intent has one; a quarantined intent may or may not (for example, one quarantined for a divergent snapshot manifest after its audit file landed). The audit file is not listed in the snapshot manifest.
- **Bounds.** `catalog_audit_partition` rejects occurrences before 1970-01-01 or after 9999-12-31 UTC (a validation error, so a quarantine), which keeps partition names fixed-width and chronological. `write_audit_records` rejects a `logical_sequence` above `i64::MAX`, since the column is `Int64`.
- **Byte-exact retry; semantic acceptance deferred.** The audit file is put with `WritePrecondition::DoesNotExist`. On a precondition failure the existing bytes are read back and accepted only when identical; anything else is `CatalogError::PreconditionFailed`, which is not retryable, so the intent is quarantined. This mirrors the snapshot manifest. Bytes are deterministic within one build of the `parquet` crate (fixed writer properties with one `created_by = arco-catalog` key-value entry, no timestamps), but the footer's `created_by` is the crate's version string and its writer defaults can change between releases, so a redelivery across a `parquet`/`arrow` upgrade fails closed, as the snapshot files already do. Accepting an existing file whose decoded rows match was deferred; see the follow-ups below.
- **Bench countdown.** Two fixtures in `crates/arco-catalog/benches/support/runtime_reuse_cost.rs` (`projection` with `interrupt`, and `conflicting_publication_is_still_quarantined`) fail the first status PUT after the publication. The audit file is one more PUT, so `fail_put_countdown` moved from 7 to 8 (5 snapshot files + audit artifact + manifest + the failing status PUT).
- **Quarantine warn log.** The materializer's non-retryable branch now logs `catalog projection intent quarantined` at warn with `record_id`, `source_sequence` and `error` before it records `INCOMPATIBLE_PROJECTION_INTENT`; before, the cause was not logged. The durable status still carries only the code. The branch for an undecodable envelope (`INVALID_PROJECTION_INTENT`) is unchanged.
- **Tests.** `parquet_util`: `audit_records_round_trip_both_row_shapes_under_the_published_schema`, `audit_record_files_are_byte_identical_for_identical_rows`, `audit_records_reject_a_logical_sequence_beyond_the_int64_column`. `catalog_authority` unit tests: `audit_partition_is_the_utc_day_of_the_occurrence`, `audit_partition_rejects_instants_without_a_four_digit_utc_date`, `audit_decoder_accepts_the_production_record_of_its_intent`, `audit_decoder_rejects_junk_and_records_of_another_intent`, `audit_artifact_path_names_the_day_sequence_and_intent`. `catalog_authority_control_v1`: planned test (b) became `materializer_writes_one_audit_artifact_per_intent` and `audit_artifact_is_written_before_acknowledgement`; also `redelivered_intent_rewrites_an_identical_audit_artifact`, `a_divergent_audit_artifact_fails_closed_without_acknowledging`, and `an_intent_whose_payload_is_not_an_audit_record_is_quarantined_without_an_artifact`.

### Package C (commit 149c63e9 and the review-fix commit 2ad3933d)

- **Report and summary.** `AuditRetentionReport` has `partitions_examined`, `partitions_unrecognized`, `partitions_expired`, `objects_deleted`, `bytes_reclaimed` and `truncated`, two fields more than planned. The worker's `AuditRetentionSummary::log` emits all six plus `elapsed_ms` at `phase="gc"`, `domain="catalog-audit"`, `outcome="ok"`. Failures are recorded as `gc[catalog-audit]: ...`; the sweep never defers.
- **Expiry rule.** `dt=D/` is expired when `D` is strictly before the UTC date `retention_days` days before `now`. The cutoff is a date, so every instant of one UTC day yields the same cutoff. A name is a day partition only in exactly the form `catalog_audit_partition` writes (`dt=` and a canonical, existing `YYYY-MM-DD` with a four-digit year); a pre-1970 day is never written but would be treated as expired. A zero `retention_days` or `max_objects` is a validation error; an empty prefix yields a default report.
- **Cursor jumps.** The sweep lists the prefix in path order in pages of at most `min(max_objects, 1000)` objects. The first object of a retained day partition ends the walk through the day partitions: the cursor jumps to `{prefix}dt=:` (`:` directly follows `9`), past every well-formed day partition, so later retained partitions are never listed. After the first object of an unrecognized directory the cursor jumps to `{prefix}{name}0` (`0` directly follows `/`), so such a directory costs one visit however many objects it holds, and one that sorts before the day partitions does not stop the sweep. A loose object directly under the prefix is its own partition. Unrecognized partitions are never deleted, logged at warn once per call, and counted in `partitions_examined` and `partitions_unrecognized`; unrecognized names that sort among the day partitions after the first retained one are skipped with them, uncounted. Nothing outside the prefix is listed or deleted (a sibling `catalog-audit-archive/` prefix is untouched).
- **Truncation.** Objects are deleted one at a time in path order, so an interrupted or truncated call leaves only the newest expired objects and the next call resumes with the oldest survivor; no cursor is persisted. When the budget is spent the walk looks for one more expired object: finding one sets `truncated`; reaching a retained day partition or the end of the listing leaves it unset. A budget-one sweep converges to the result of one unbounded sweep, one call per expired object. Storage errors stay storage errors and name the listing cursor or the object; objects deleted before an error stay deleted.
- **Dedicated budget instead of GC-page scaling.** The first cut derived the per-run budget from the GC page setting (`ARCO_CONTROL_STORE_GC_MAX_PAGES` x 1000, so 16,000 by default, about 320 to 800 s of serial deletes). Review replaced it with `ARCO_CONTROL_STORE_AUDIT_SWEEP_MAX_OBJECTS` (`DEFAULT_AUDIT_SWEEP_MAX_OBJECTS = 4096`): at about 20 to 50 ms per delete on GCS a full run takes about 80 to 200 s, inside the 5-minute schedule and the 1800 s task timeout. The GC page budget no longer affects the sweep. Overlapping sweeps are harmless (deleting a missing object succeeds) and only double-count their summary fields.
- **30-day floor.** `ARCO_CONTROL_STORE_AUDIT_RETENTION_DAYS` defaults to `CATALOG_AUDIT_RETENTION_DAYS` (400). The worker rejects a value below `MIN_AUDIT_RETENTION_DAYS` (30) at startup; the kernel sweep accepts any retention of at least one day.
- **Settings parser.** `usize_env(name, default)`, which read the process environment and parsed only `usize`, was replaced by the generic `positive_setting<T>` over an injected lookup and `RunLimits::from_settings(|name| std::env::var(name).ok())`. An unset or blank setting takes its default; zero or a non-integer is rejected with the same messages as before. Tests pass settings as pairs instead of mutating the process environment. The startup log line gains `audit_retention_days` and `audit_sweep_max_objects`.
- **Accepted edge.** The sweep does not coordinate with the drain. A redelivered intent whose partition already expired rewrites its file, and the next sweep deletes it again. A sweep that deletes the file between a redelivery's failed does-not-exist put and its read-back makes the read report `NotFound`, which is not retryable, so the intent is quarantined. Both need an intent left unacknowledged, or redelivered, for longer than the retention.
- **Tests.** `catalog_authority_control_v1`: `audit_sweep_expires_only_partitions_strictly_older_than_the_retention` (401/400/399-day and today partitions plus unrecognized names before, among and after the day partitions, and a sibling prefix), `audit_sweep_with_a_budget_of_one_converges_to_the_single_sweep_result`, `audit_sweep_budget_truncates_and_later_calls_finish_the_partition`, `audit_sweep_cutoff_is_a_utc_date_not_an_instant`, `audit_sweep_visits_an_unrecognized_directory_once`, `audit_sweep_storage_errors_stay_storage_errors_and_name_the_object_or_listing`, `audit_sweep_rejects_a_zero_retention_or_budget_and_is_idle_on_an_empty_prefix`. Worker: `run_once_expires_old_audit_partitions_in_the_gc_phase`, `run_once_records_an_audit_sweep_failure_as_a_gc_failure`, `run_limits_default_the_audit_retention_to_400_days_and_reject_zero`, `run_limits_floor_the_audit_retention_at_30_days`, `run_limits_read_the_audit_sweep_budget_independently_of_gc_pages`.

### Follow-ups (not fixed in step 3)

1. **Catalog snapshot directories are never collected.** Every acknowledged catalog intent publishes a full catalog snapshot under `control/v1/projections/catalog-parquet/{source_logical_sequence:020}-{source_authority_manifest_id}/`, and nothing deletes it: the kernel GC is scoped to `control/v1/domains/<domain>/`, the legacy GC to `snapshots/`, and the audit sweep to `control/v1/projections/catalog-audit/`. Growth is one full snapshot per mutation, unbounded. The design assumed a projection GC that "already ages superseded snapshots"; none exists.
2. **Semantic retry acceptance for projection Parquet.** Accept an existing file whose decoded rows match instead of requiring identical bytes. It must land no later than step 4, because restore-emitted audit records may be written without snapshot files. Until then, drain the catalog outbox before deploying a different `parquet`/`arrow` version; the API (post-commit and operator drains) and the worker must run the same version.
3. **Restore-emitted audit record.** Moved to step 4.
4. **Post-purge keyed-id collision.** Documented behaviour (see Package A): a keyed retry after its receipt was purged fails closed with `AlreadyExists { entity: "projection intent" }` until the earlier intent is drained and trimmed. A per-call operation id would remove the collision; that is an owner decision.
5. **Audit partition compaction.** One single-row file per mutation (about 173,000 files a day at the pilot rate); compacting day partitions into larger files is open.
6. **Residual tag-4 rows.** Format-9 roots written before step 3 may still hold audit rows under the reserved tag 4; nothing expires or deletes them.
