# Retention step 3: receipt expiry, audit-row removal, audit projection — implementation plan

> **Execution contract:** implement package-by-package with TDD, one implementer per package, a two-stage (spec, then quality) review after each package, and no package starting before the previous one is approved. Design: `2026-09-26-state-store-retention-design.md` (accepted). Steps 1 (PR #439) and 2 (PR #442) are on `main`.

**Goal:** The catalog adapter stops writing audit rows to the authoritative KV and writes idempotency receipts with a 24-hour expiry hint; the catalog projection materializer appends every audit record to a day-partitioned `system.catalog.audit` Parquet artifact before it acknowledges the intent; a retention sweep ages audit partitions (default 400 days). No restore-path changes (the restore-emitted audit record moves to step 4 because the restore code was rewritten on `main` after step 2).

**Architecture:** `stage_commit_records` (`crates/arco-catalog/src/catalog_authority.rs` ~:2922) keeps the receipt (key tag 3) and the projection intent whose payload is the audit record, and drops the audit row (key tag 4) and its `assert_absent`. The receipt is written with `ArcoStateTxn::put_with_expiry` at `occurred_at_ms + 24 h` (format 9; the test-only bounded format 8 refuses expiry, so its v2 path keeps a plain put). `CatalogProjectionMaterializer::materialize` (~:1040) decodes the intent payload and writes one immutable Parquet file per intent under `control/v1/projections/catalog-audit/dt=YYYY-MM-DD/` (day of `occurred_at_ms`, UTC) with a does-not-exist precondition and byte-identical retry acceptance, exactly as the snapshot manifest is written, so artifact-before-ack ordering holds and at-least-once redelivery is idempotent. A retention sweep on the materializer deletes partitions older than the retention; the control-store worker calls it in its GC phase. Nothing under `control/v1/projections/` is touched by the kernel GC (domain-scoped to `control/v1/domains/<domain>`) or the legacy GC (`snapshots/` only).

**Tech stack:** Rust 1.88, Arrow/Parquet (already used by `parquet_util`), Tokio; test harness in `crates/arco-catalog/tests/catalog_authority_control_v1.rs` (`scoped_storage()`, `scope()`, `RecordingProjectionNotifier`, `commit_burst_and_settle`) and the worker binary's tests.

## As implemented

### Package A (commit e3371549 and the review-fix commit after it)

- **Completion.** The Package A implementer was interrupted mid-package; the lead finished it (commit e3371549), and a review round followed with the fixes recorded below.
- **Retired tag kept for the fixture.** `AUDIT_KEY_TAG` and `audit_key` were not removed. They survive under `cfg(any(test, feature = "test-utils"))` because the authority-8 synthetic-genesis cost fixture (`bounded_capacity_v2_record_pair`) models the pre-step-3 row shape its recorded bounded cost measurements were taken with. The format-9 `capacity_fixture_record` models receipts only. Tag 4 is documented as reserved forever: format-9 roots written before step 3 may still hold tag-4 rows, and nothing expires or deletes them.
- **Receipt retention contract.** `CATALOG_RECEIPT_RETENTION_MS` is re-exported at the crate root. A keyed request stays replayable with its original response for at least 24 hours from when the adapter accepted it (the audit record's `occurredAtMs`); the horizon adds its one-hour skew margin, so a receipt is first purgeable strictly after `occurredAtMs + 25 h`. The hint is written on format 9 only; the test-only bounded format 8 writes plain receipts. Once a receipt is purged its key is free: a different same-family request under that key is no longer an idempotency conflict, and an identical one re-executes. Unkeyed mutations also write a receipt (keyed by their random operation id) with the same expiry, so the horizon purges those too.
- **Deterministic operation ids (decision).** Keyed operation ids stay deterministic per (operation family, idempotency key), as the accepted design's family-qualified operation id requires, and the projection intent id equals the operation id. Consequence: a keyed request replayed after its receipt was purged re-executes under the same id. While the earlier intent is still retained in the outbox, staging fails closed with `CatalogError::AlreadyExists { entity: "projection intent", .. }` before commit (no receipt, no mutation). Once the materializer drains and trims that intent, the retry commits and stages a fresh outbox incarnation of the same id at a higher origin sequence. The downstream audit identity is therefore `(operation_id, logical_sequence)`, not `operation_id` alone; Package B's artifact path (`{source_logical_sequence:020}-{intent_id}.parquet`) already encodes that pair.
- **Tests rewritten** because they encoded audit rows in the KV: the cross-family idempotency test (now `shared_idempotency_key_across_families_keeps_every_intent_and_no_audit_row`: zero tag-4 rows, three audit intents with the three families); the lost-response reconciliation test (zero tag-4 rows, the intent's family); `control_bounded_parity` (no tag-4 write, and its undeclared-writes check enforces that none is written; the intent payload is still compared to the expected audit record); the bounded unit tests (audit history read from the notified intents); the `capacity_design` smoke test and the `gate7_capacity` probe (one receipt per mutation).
- **Tests added.** `receipt_expiry_tests` (exact staged write shape on both formats; committed state holds the receipt and no audit row). `receipts_expire_after_the_retention_window_and_the_replay_reapplies` pins the catalog name conflict (`AlreadyExists { entity: "catalog", name: "analytics" }`): the command's name check runs before the commit records are staged, so it fires even though the first intent is still retained. `a_purged_receipt_lets_a_keyed_patch_reapply_once_its_intent_is_trimmed` walks the post-purge path above (two receipts purged, the replay fails closed on the intent id with no new receipt, then drain and trim, then the replay commits one receipt and one intent of the same id at origin sequence 4 against the original 2). `a_receipt_becomes_purge_eligible_strictly_after_twenty_five_hours` pins the horizon boundary (no eligible row at `occurredAtMs + 25 h`, eligible one millisecond later).
- **Capacity probes.** The `gate7_capacity` report's status is `pilot-blocked-without-retention-horizon` with `retention_horizon_modelled: false`: a week of receipts still exceeds the unchanged restore scanner because the probe models no horizon purge. The ignored `capacity_design` encoding experiment now gives every synthetic receipt row a production-shaped expiry hint (fixed base clock, monotone), so the nullable expiry column is populated.
